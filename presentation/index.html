Proof of concept · Monday presentation

Right-sized specification before code.

Adaptive SDD puts TinySpec, LiteSpec, and official GitHub Spec Kit behind one guided workflow—so teams create enough shared understanding without defaulting to maximum ceremony.

One orchestrator One question at a time Approval gates Traceable evidence
Adaptive SDD POCJonC613/adaptive-sdd
Talk track: Open with the problem, not the tooling. The goal is not more documentation. The goal is to make intent, boundaries, risk, and evidence clear before implementation—using the least process that safely works.

01 · The problem

Teams usually get two bad defaults.

Too little

“Just build it”

  • Hidden assumptions surface during implementation
  • Acceptance becomes subjective
  • Tests prove code paths, not necessarily intent
Too much

Full process for every change

  • Small work receives heavyweight ceremony
  • Artifacts become repetitive or stale
  • People route around the process
The gap is proportionalityUse the least ceremony that preserves clarity
Talk track: Most teams recognize both failure modes. Adaptive SDD addresses the space between a prompt and full Spec Kit. Emphasize that complexity is driven by uncertainty and blast radius—not merely estimated lines of code.

02 · The model

Three tiers. One entry point.

1 artifact

TinySpec

Bounded, reversible, understood work with one clear implementation path.

.tinyspec/feature.md

3 artifacts

LiteSpec

Several stories, meaningful decisions, phased delivery, or acceptance-to-test traceability.

spec.md · plan.md · tests.md

Full workflow

GitHub Spec Kit

Major architecture, migrations, regulated behavior, complex integrations, or multi-team coordination.

Official upstream workflow

No scorecard automatically chooses a tierRationale + user confirmation
Talk track: TinySpec is one compact contract. LiteSpec separates what, how, and proof. Full Spec Kit remains GitHub's official upstream workflow. Adaptive SDD does not fork or dilute Spec Kit; it routes to it when the work warrants it.

03 · User experience

The orchestrator guides the whole journey.

1 · InspectRead codebase, tests, conventions, and deployment surface
2 · RecommendExplain the smallest suitable tier and why
3 · DiscoverAsk one focused question at a time
4 · ApproveGate artifacts explicitly before moving forward
5 · ProveMap intent to tasks, tests, and release evidence

Approval of artifacts is not permission to implement. Code changes require a separate, explicit authorization.

Codex: $adaptive-sddCursor: /adaptive-sdd
Talk track: The user does not have to learn multiple commands or decide the tier alone. The skill inspects first, explains its recommendation, and asks for confirmation. Discovery remains conversational rather than dumping a questionnaire.

One compact build contract

What it describes

  • Three-column personal Kanban
  • Create, edit, move, and delete tasks
  • Browser-local persistence
  • Responsive and accessible behavior

Open the TinySpec exampleBest when one file remains sufficient
Talk track: This is the low-ceremony path. It is still a specification: outcome, context, requirements, plan, tasks, and completion evidence are all present. It avoids pretending a small feature needs an elaborate lifecycle.

05 · Same product, more depth

LiteSpec separates intent, delivery, and proof.

What + why

spec.md

Five user stories, rationale, observable acceptance criteria, edge cases, boundaries, and non-functional requirements.

How

plan.md

Technical decisions, impacted areas, risks, dependencies, implementation phases, verification, and rollback.

Evidence

tests.md

Twelve acceptance criteria mapped to automated evidence, plus failure, accessibility, responsive, and touch considerations.

Open the LiteSpec exampleEach artifact has its own approval gate
Talk track: The value is not simply “more text.” Each file answers a different question. Stable IDs let the team follow a requirement through implementation and evidence. The Kanban example contains both Tiny and Lite versions specifically to make this contrast visible.

06 · The proof chain

Intent remains connected to evidence.

US-04

As a returning user, restore my board.

AC-04.2

Unreadable storage still yields a usable board.

P1-T1

Implement restoration-safe task state.

T-09

Exercise invalid JSON and storage failures.

Evidence

Pass result linked to the release decision.

A reviewer can ask “why does this code exist?” and follow the answer in either direction.

Stable IDs reduce ambiguityValidators detect orphaned or incoherent artifacts
Talk track: Walk left to right, then right to left. The validator does not decide whether a requirement is good, but it can deterministically detect broken metadata, missing mappings, duplicate IDs, and version inconsistencies.

07 · POC evidence

What Kanban proves today.

  • The same feature can be expressed at two useful depths
  • TinySpec stays genuinely compact at one artifact
  • LiteSpec produces exactly three gated artifacts
  • User stories include rationale and edge cases
  • Acceptance criteria map to implementation and tests
  • Validators enforce lifecycle and traceability structure
  • The workflow can reach a deployed, functioning product
  • Documentation can remain inspectable from the product
POC conclusion: the mechanism works end to endControlled example, not enterprise validation
Talk track: Be confident but precise. The project demonstrates feasibility and provides a concrete artifact set. It is not evidence that every team or every production system will adopt the workflow successfully.

08 · Honest limitations

What Kanban does not prove yet.

Adoption

  • A colleague can install and use it without coaching
  • Codex and Cursor produce acceptably consistent outcomes
  • The artifact burden feels proportional in routine work

Production complexity

  • Real repository conventions and legacy constraints
  • Cross-system contracts, security, or migrations
  • Reliable promotion from LiteSpec to full Spec Kit
Current app implementation is maintained in a separate repositoryTouch and responsive visual checks remain explicit manual evidence
Talk track: Calling these limitations out strengthens the proposal. The correct conclusion is “ready for a bounded pilot,” not “ready for organization-wide rollout.” The separate app repository should be linked directly when showing implementation evidence.

09 · Next proof

Run one small, work-shaped pilot.

Choose

A safe feature in an existing codebase: filtered export, approval status, notification preference, API field, or admin action.

Require

At least one existing convention, one failure path, one technical decision, and one regression boundary.

Avoid

Regulated data, irreversible migrations, broad architecture changes, or a deadline-critical production release.

Recommended tier: LiteSpecTarget: 60–90 minute guided exercise
Talk track: The pilot should be real enough to encounter constraints, but safe enough to stop. LiteSpec is the best test because it exercises the differentiating middle tier. Keep production rollout out of scope.

10 · Repeatable test

Test the workflow, not just the output.

Fresh startInstall into a clean checkout from written instructions
Minimal promptProvide only a short, realistic feature request
Independent useLet a colleague complete discovery and approvals
ImplementAuthorize code only after all artifacts validate
AmendChange one requirement and check propagation
Record screen, elapsed time, questions, corrections, and test resultsDo not coach unless blocked
Talk track: A successful artifact set created by the author is weaker evidence than a colleague independently using the instructions. Introduce one small change after approval to test whether the amendment workflow prevents silent drift.

14 · Proven foundations

Adaptation, not invention from scratch.

Workflow and requirements

  • GitHub Spec Kit — phased specification workflow
  • Agile Alliance — user stories and evolving detail
  • Cucumber Gherkin — observable Given/When/Then examples

Decisions, testing, and change

  • Test Pyramid — lowest practical test layer
  • Lightweight decision records — context and consequences
  • Semantic Versioning — adapted for specification amendments
LiteSpec combines established practices while reducing artifact countSources are documented in the repository
Talk track: Adaptive SDD's contribution is packaging and proportionality. It reuses known techniques: phased specs, value-centered stories, observable acceptance, traceability, lightweight decisions, and layered testing.
